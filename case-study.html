The problem

A zero-knowledge proof can verify perfectly and still back the wrong payment. In proof-gatekeeper tasks the danger is not an invalid proof — it is a valid proof attached to a request whose fields do not add up: a substituted verification key, a replayed proof reference, a balance below the minimum, an expired block window, a different recipient, or an amount over the transfer cap.

An agent that only asks “does this proof verify?” approves roughly half the traps. The check has to happen field by field, before any approval.

What this agent does

  • Receives signed task envelopes over HTTPS and authenticates every request with HMAC-SHA256 over the raw body before parsing.
  • Runs deterministic checks in fixed order — reuse → VK match → threshold → recipient → amount cap → expiry — and fails closed on anything malformed.
  • Mints its own Groth16 proof (official gatekeeper circuit, snarkjs) that the decision followed the rule, and verifies that proof locally against the circuit verification key before returning it.
  • Signs every response, deduplicates retries by task id, and keeps a durable seen-set of proof references.

Why it matters

Payment agents sit between a cryptographic claim and a real transfer. Treating “the proof verifies” as the end of the check is the failure mode this design removes: validity is necessary, not sufficient. The agent proves what it decided and why, so the judgment is auditable without revealing anything beyond the decision itself. The same pattern applies to escrow release, treasury operations, and any workflow where an agent signs off on proof-backed claims.

Build
